## Sign convention (resolved)
The original `skempi_eval.py` stores the **raw** `binding_ddG_pred` (line 48) and
does **NOT** multiply by -1. Only the separate `run_stabddg.py` applies x-1
(line 37). The reproduced baseline CSV was generated by `skempi_eval.py` and is
**positively** correlated with ground-truth ddG (overall Spearman 0.531, matching
its metrics txt; sanity Pearson vs author StaB-ddG.csv = 0.9908). Therefore
`run.eval.write_csv` mirrors `skempi_eval.py` exactly: **no x-1**, raw prediction
under `ddG_pred`, `to_csv` without `index=False`.

## Bug found & fixed (GPU-only, surfaced by this smoke)
`track_esm3/esm3_scorer.py` failed on the FIRST real GPU complex with:
```
RuntimeError: mat1 and mat2 must have the same dtype, but got Float and BFloat16
  at esm/models/esm3.py:109  plddt_embed = self.plddt_projection(rbf_16_fn(average_plddt))
```
Root cause: on GPU the ESM3 model params are bfloat16, but `ESM3.forward`
internally forces `average_plddt`/`per_res_plddt` to `.float()` (esm3.py:334-335),
so a float32 tensor feeds the bf16 `plddt_projection` Linear. The existing ESM3
tests only ran on **CPU (float32)**, so this path was never exercised. Fix: run
the ESM3 forward under `torch.autocast(device_type="cuda", dtype=model_dtype,
enabled=use_autocast)` where `use_autocast` is True only on a non-fp32 CUDA model
(no-op on CPU). The CPU `test_wt_ddG_zero_singlechain` still passes (wt ddG ~= 0),
confirming CPU behavior is unchanged.
